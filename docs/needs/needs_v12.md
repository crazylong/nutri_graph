## 一、需求简述
```
1.增加后台用户列表页面，后台用户跟企业知识库用户用同一套用户体系；
  1.1 后台登陆的新用户默认：default_renter 租户，这期演示版本默认都是管理员；
  1.2 管理员可以查询所有租户数据；
  1.3 管理员账号可以把非管理员设为管理员；
  1.4 管理员是用户表的一个字段，不做角色体系；
  1.5 写死 13451527374 是超级管理员，可以把管理员设为非管理员，在.env配置；
  1.6 列表页支持新增、修改、删除用户，不能修改手机号，可以修改用户名、角色，管理员不能删除，通过手动新增的用户可以设置用户角色是管理员/普通用户。
2.企业知识库问答系统增加登陆功能，需要做「不存在的用户不能登录」的反向限制，登陆的时候需要填写租户名（必填），就算这个账号是管理员，也要指定租户名，这一版做演示默认登陆页面设置：default_renter，用户可以改。
3.食疗后台增加多租户列表页面，页面支持新增、删除、租户名不能修改、增加/删除用户操作，数据库插入一条默认租户：default_renter，之前的老用户都放到default_renter下面，
4.食疗前台用户跟后台用户隔离，这个可以看成企业客户。
5.后台增加客户列表页面，只能查询，暂时不做增、删、改操作。

统一概念：
后台用户：即养生了么这家企业的员工，可以使用后台页面跟知识问答页面；
租户：对后台用户的分类；
知识问答页面用户：数据基于后台用户；
企业客户：养生了么这家企业的客户，只能访问养生了么前台的食疗问答。
企业客户不能跟后台用户共用一个表通过user_kind区分，一是业务隔离，二是这个用户既是后台用户又是企业客户就不好区分。
```


## 二、需求详述

> 性质：这是**需求文档**（概念模型 + 逐条理解 + 与现状的关系），不是实施方案。方案留给 plan_v12。
> 本节是对需求简述的**复述与展开**，把「统一概念」里四类主体的关系和每条需求要做什么讲清楚；有歧义、不合理、需补充的地方集中在第三节「需求补充」。

### 2.0 概念模型（四类主体）

先厘清四个名词，后面每条需求都挂在这套概念上：

| 名词 | 是谁 | 用什么承载 | 能访问什么 |
|---|---|---|---|
| **后台用户** | 养生了么这家企业的**员工** | `app_user`（现有账号表） | 后台管理页 + 企业知识库问答页 |
| **租户** | 对后台用户的**分类**（一个员工可属一个或多个租户） | 新增 `tenant` 表 + 用户-租户关联 | — |
| **知识问答页用户** | 数据**基于后台用户**（即 kb 问答登录的就是员工本人） | 复用 `app_user`，不另建表 | 企业知识库问答页 |
| **企业客户** | 养生了么的**客户** | 新增 `customer` 表（**独立，不共用 `app_user`**） | 只能访问食疗前台 |

**核心结论（第 20 条定死）**：企业客户和后台用户**分两张表**，不能用 `user_kind` 字段区分。理由是业务隔离 + 一个人可能既是员工又是客户，单表字段区分会二义。因此：

- 后台用户 + 知识问答用户 = 同一批人 = `app_user`（员工）。
- 企业客户 = 另一批人 = `customer` 表（食疗前台 C 端）。

### 2.1 逐条需求

#### 需求 1：后台用户列表页面

- **1.1 后台登录新用户默认 `default_renter` 租户 + 默认管理员**：员工从后台登录（`/auth/token` 带 `console=true`）时，若该手机号尚未在 `app_user`，自动建号，`role=admin`，并挂到默认租户 `default_renter`。
- **1.2 管理员可查所有租户数据**：管理员自身可以零租户，但后台列表/租户列表/文档查询**不按调用者所属租户过滤**，能看全量。
- **1.3 管理员可把非管理员设为管理员**：`role` 是 `user`/`admin` 两值字段，管理员有权把 `user` 升为 `admin`。
- **1.4 管理员是字段，不做角色体系**：只有 `user`/`admin` 两个值，不引入 RBAC/角色表。
- **1.5 超管 13451527374 在 .env 配置**：超管是配置里的手机号，不是第三种 `role`。它可以把管理员降为普通用户（普通管理员无此权限）。
- **1.6 增删改用户**：列表支持新增、修改、删除。**手机号不可改**；可改用户名、角色；**管理员不能删除**；手动新增的用户可设角色为管理员/普通用户。

#### 需求 2：企业知识库问答加登录（反向限制 + 必填租户名）

- kb 问答页从「匿名 `client_id`」改为「登录态」。
- **反向限制**：登录时「不存在的用户不能登录」（即员工必须先存在于 `app_user`，由后台登录/管理员新增产生），**不自动建号**——这与主站「未注册即建号」语义相反。
- **必填租户名 + 归属校验**：登录时必填租户名（默认 `default_renter`，可改）。**校验「用户存在」+「用户属于所填租户」**，两者任一不满足都提示「用户不存在」。管理员也要指定租户名（在 kb 问答页只检索所填租户）；管理员「查所有租户」只体现在后台文档列表，不在 kb 问答页。

#### 需求 3：多租户列表页面

- 后台新增租户列表页：支持**新增、删除**租户；**租户名不能修改**；支持**增加/删除用户**（把员工挂进/移出租户）。
- **默认租户**：数据库插入一条 `default_renter`。
- **老用户回填**：之前的老用户（现有 `app_user` 存量）都挂到 `default_renter` 下。

#### 需求 4：食疗前台用户与后台用户隔离

- 食疗前台用户 = **企业客户**，后台用户 = **员工**，两者**分表隔离**（第 20 条明确否决 `user_kind` 共表）。
- 企业客户只能访问食疗前台问答，不能进后台、不能进 kb 问答。

#### 需求 5：客户列表页面

- 后台新增客户列表页（查 `customer` 表），**只查询**，暂不做增删改。

### 2.2 与现状的关系

| 现状资产 | 出处 | 本需求怎么用 |
|---|---|---|
| `app_user` 账号表（手机号三态 + `role` + `status`） | `migrations/001_auth.sql`、`api/auth.py` | **作为「后台用户（员工）」表**，加 `username`；企业客户从里面拆出去 |
| 验证码登录 `/auth/sms` + `/auth/token`（`console=true` 升管理员） | `api/auth.py` | 后台登录沿用；kb 登录复用但加「反向限制」（不建号） |
| `require_admin` / `get_current_user` | `api/deps.py` | 后台用户列表、租户列表、客户列表、kb 登录都挂鉴权 |
| kb 问答匿名 `client_id` 会话 | `api/kb.py`、`kb/memory.py` | 改为登录态（`kb:`+user_id），匿名会话废弃 |
| 租户只是 `kb_document.tenant_id` 文本 | `kb/store.py` `list_tenants()` | 升级为 `tenant` 表 + 关联表，文档 `tenant_id` 保持 TEXT |
| 食疗前台 `/chat` 登录用户（现也在 `app_user`） | `api/chat.py` `get_principal` | **拆到 `customer` 表**，与企业客户对齐 |

### 4.1 结论

需求合理，可以写 plan_v12。核心是把「四类主体」的边界钉死，并据此定施工口径：

1. **分表，不用 `user_kind`**（第 20 条 + 3.1 拍板）：后台用户（员工）留在 `app_user`；企业客户拆到新表 `customer`。食疗前台登录改写 `customer`，后台登录写 `app_user`。
2. **kb 登录做归属校验**（3.3 拍板）：登录必填租户名，校验「用户存在」且「用户属于所填租户」，任一不满足都提示「用户不存在」。「管理员查所有租户」只体现在后台文档列表，不在 kb 问答页。
3. **租户实体化 + 默认租户回填**（3.5 拍板）：`tenant` + `tenant_user`，只挂员工；`customer` 无租户概念；存量 `app_user` 全部回填 `default_renter`。
4. **超管是配置号，不是第三种角色**（3.4 拍板）：`SUPER_ADMIN_PHONE` 在 .env，超管也挂 `default_renter`，自己不可降级/删除。

下面 4.2 是施工口径，4.3 是需求覆盖核对。

### 4.2 施工口径（写 plan 时照此执行）

**4.2.1 分表：`app_user`（员工）与 `customer`（企业客户）**

- 新增 `customer` 表，复用 `security.crypto` 的手机号三态（`phone_hash`/`phone_enc`/`phone_mask`）。
- `/auth/token` 改造：不带 `console` → 写 `customer`（企业客户）；带 `console=true` → 写 `app_user`（员工，`role=admin`，挂 `default_renter`）。**两条路物理分离，不再共写一张表。**
- 匿名身份（`typ=anon`）仍是临时身份，不落 `customer` 行（3.1 拍板）。
- 存量 `app_user` 里的 C 端用户**不迁移**（3.1 拍板：演示期无真实客户）。
- `require_admin`、`get_current_user` 仍然查 `app_user`（后台体系不变）；食疗前台的 `get_principal` 登录态要指向 `customer`。

**4.2.2 后台用户列表（需求 1）**

- `app_user` 加 `username TEXT NOT NULL DEFAULT ''`（展示名，3.6 拍板）。
- 接口 `api/admin_users.py`（挂 `require_admin`）：GET 列表 / POST 新增 / PUT 修改 / DELETE 删除。
- **权限矩阵**：
  - 删管理员 → 409；删超管 → 409；删普通用户 → 放行（硬删 `DELETE FROM app_user`）。
  - 降级管理员为普通用户 → 只有超管能做（普通管理员 403）；超管自己不可降级/删除。
  - 升普通用户为管理员 → 任意管理员可做。
  - 新增时手机号已存在 → 409 `phone_exists`，不覆盖原行角色（防止普通管理员借「新增」改别人角色）。
- 手机号不可改（PUT 不收 phone）；`username`/`role`/租户归属可改。

**4.2.3 kb 登录（需求 2）：反向限制 + 归属校验**

- `/auth/token` 加 `no_create` 标志：为真时不建号，先查 `app_user` 是否存在；不存在返回 401 `user_not_found`。
- **归属校验（3.3 拍板）**：登录还要校验「该 `user_id` 是否属于所填租户名」（查 `tenant_user` 关联）。用户不存在、或不属于该租户，**都提示「用户不存在」**（对外不区分两种失败，避免枚举）。
- 登录必填租户名，默认 `default_renter`，可改。
- kb 问答端点（`/kb/ask`、`/kb/ask/stream`、`/kb/sessions`、`/kb/recent`、`/kb/sessions/{id}`）改为登录态 `get_current_user`，会话键 `kb:` + `user_id`。
- 老匿名 `client_id` 会话废弃，不迁移。
- **检索租户**：kb 问答检索的 `tenant_id` 来自登录时选定的租户名（`/kb/ask*` 的 `tenant_id` 参数即此值）。

**4.2.4 多租户（需求 3）**

- `tenant` 表（`id`/`name` 唯一/`created_at`）+ `tenant_user` 关联表（`tenant_id`+`user_id` 主键，级联删除）。
- **租户名不可修改**，无改名端点。
- 迁移回填：插入 `default_renter`；把存量 `kb_document` 里 DISTINCT 的合法 `tenant_id` 回填 `tenant`（防孤儿）；把存量 active 的 `app_user` 全部挂 `default_renter`（3.5 拍板，`customer` 不参与）。
- 接口 `api/admin_tenants.py`：GET 列表 / POST 新增 / DELETE 删除（有文档禁删 409）/ 增加用户 / 移除用户。
- `kb_document.tenant_id` 保持 TEXT 不改成外键；`/kb/tenants` 改读 `tenant` 表。

**4.2.5 客户列表（需求 5）**

- 只读，查 `customer` 表，字段：**手机号（掩码）、创建时间范围**（3.6 拍板）。不做增删改。

**4.2.6 删除连带（3.6 拍板）**

- 删除后台用户：硬删 `app_user` 行，`refresh_token`/`user_consent`/`tenant_user` 靠 `ON DELETE CASCADE`；`kb:{user_id}` 旧会话留着不动。

### 5.1 结论

可以写 plan_v12 的主体。本期不做「把管理员设为普通用户」。企业客户和员工按两套业务实现。手工建号挂默认租户、租户名即文档 `tenant_id`，这两条按原复审建议执行。存量 `app_user` 里的食疗前台账号删除，只保留后台账号，不迁到 `customer`。

### 5.2 已拍板

**1. 本期不做降级**

需求 1.5、3.4、4.2.2 里「超管把管理员降为普通用户」本期不做，先做主功能。不增加 `SUPER_ADMIN_PHONE`，不做降级接口，用户页也不能把 `admin` 改成 `user`。

本期仍然做：

- 新建用户时可以指定管理员或普通用户（1.6）。
- 管理员可以把普通用户升为管理员（1.3）。
- 管理员不能删除（1.6）。普通用户可以删除。

一个号一旦是管理员，本期不能改回普通用户，也不能删。误设要等以后做降级再处理。

**2. 企业客户和员工是两套业务**

`customer` 与 `app_user` 分表，不用 `user_kind`。匿名身份不落客户行。客户没有租户。

代码能共用就共用，共用不上就另写。手机号三态（`security.crypto`）和短信通道可以共用。登录、刷新令牌、同意记录、鉴权查表现在都挂在 `app_user` 的外键上，客户塞不进去就另写一套，不为了复用去改员工表的外键。具体拆到哪一层交给 plan，这里不指定表名和字段。

食疗前台登录写 `customer`。知识库「不存在不能登录」只约束知识库，前台仍然是登录即建客户。员工令牌不能直接调食疗前台；同一个人要进前台，在前台再用同一手机号登录，另建一行客户。

**3. 手工新增默认挂 `default_renter`，用户页不改租户**

- 手工新增挂 `default_renter`，角色按表单指定。没有租户关系的人，按 3.3 会在知识库登录页被当成「用户不存在」。
- 之后的加入、移出只在租户页做。
- 用户页修改只收用户名和角色，不收手机号，不收租户。角色只能从普通用户升为管理员，不能反向，避免用户页变成第二套降级入口。
- 手机号已存在则 409，不改原行的角色和租户。

**4. 租户名就是文档上的 `tenant_id`，`default_renter` 不能删**

- `tenant` 以名字做主键。这个字符串就是 `kb_document.tenant_id`，也是登录时填的租户名。不再另设可改的显示名。
- 新建时必须通过现有 `TENANT_RE`（字母、数字、下划线，最长 32）。重名 409。没有改名接口。
- `default_renter` 禁止删除。其他租户名下已有文档时也禁止删除。没有文档的可以删，关联行随之删掉，员工账号保留。
- 迁移插入 `default_renter`，并把存量文档里合法的 `tenant_id` 补进 `tenant` 表。这些补出来的租户默认没有成员。留下的后台账号挂 `default_renter`（见下一条）。除默认租户外，已有文档的租户在有人被挂进去之前，知识库谁都登不进。

**5. 存量食疗前台账号删除，只留后台账号**

不迁到 `customer`。这条覆盖 3.1 第 2 条「不迁移」，也覆盖 4.2.4「全部 active 的 `app_user` 都挂默认租户」。

食疗前台下次登录会新建客户行。哪些行算前台账号、名下会话删不删，见 5.3 第 3 条。那条拍板之前，plan 不写删除脚本。
