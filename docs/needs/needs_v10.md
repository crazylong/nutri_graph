### 2.0 定位与边界

这是一个**面试演示项目**，主线是「文档（图文）的加载 → 嵌入 → 检索」，落成一条能跑通、能讲清楚、能评测的多模态 RAG 流水线。它与现有项目的关系是一句话：**同一套基础设施（Milvus / PostgreSQL / DashScope / LangGraph / trace），换一个业务载体（部门制度、方案设计等企业文档），并且第一次把「图片」当一等公民纳入检索。**

据此先划三条边界，避免把它和食疗线搅在一起：

1. **补充，不是改造（第 10 条已定）**：企业知识库是在原项目上**新增**的独立演示能力，不要求改动食疗问答的既有链路、证据分层、审核闭环。原项目「业务数据录入」与本主题「内部知识快速检索」各管各，数据互相隔离。两条线在「评估、trace、多租户」三处可以共享同一套方法论与代码。
2. **demo 优先，可控优先**：目标是面试能讲清「图文互搜怎么实现、评估怎么观察、多租户怎么隔离」，而不是做成可上线的企业级产品。能用现成组件（Milvus 混合检索、DashScope 多模态嵌入）就不用自研。
3. **图片是一等公民**：这是本主题区别于现有 `kb_chunks`（纯文本降级检索）的核心卖点。图片不以 OCR 抽字了事，而要保留图本身的语义。

### 2.3 各条展开

**KB-01 文档格式。** 三种格式收敛成同一「块」模型：`(text, 块类型, page_no, bbox, 标题链)`，其中**块类型**取值正文 / 图片（这是版面类型，**不叫 `doc_kind`**，与第 12 条的「技术类/制度类」文档分类是两回事）。Markdown 走标题/语义切分，PDF 走版面解析（标题层级 + 图片坐标），DOCX 走段落/图片抽取。`page_no`、`bbox` 允许为空（Markdown 图是独立文件、DOCX 图无稳定页坐标）。**验收口径**：同一个问题，md / pdf / docx 三种格式都能召回该文档的对应章节（「切块边界一致/块语义一致」不做判定——分页、页眉、样式都会让三种格式的切块边界不同）。

**KB-02 图文互搜。** 两个方向各走各的**独立向量**，落在模型内部的同一图文对齐空间里（百炼 `MultiModalEmbedding` 的「独立向量」= 以文搜图、以图搜文）：文本块走文本塔、图片块走图像塔，文本提问能召回图（语义对齐 + 描述上的 BM25 两条腿），图片提问能召回图文块（纯图走图像塔，与图片块的图像塔向量同路径对称）。图片块仍生成上下文描述，但描述**只写进 `text` 字段**供 BM25 和回答用，**不进稠密向量**。**图片提问与入库完全对称**：纯图 → 图像塔向量，不拿纯图去比「图+描述」融合向量（融合向量是另一种返回类型 `fused`，与纯文本/纯图向量无可比性保证）。验收：用一张架构图入库，问「这张架构图讲了什么」能召回该图；用图提问能命中含对应文字的文档块。

**KB-03 评估可观察。** 分层评估、**只观察不干预**：① 离线 Ragas（有据问答跑 faithfulness / context precision / answer relevancy 三项）做回归；② 图文召回跑双向 Recall@K（R@1/R@5/R@10，可附 MRR），见 2.7。评估结果**能打开看**——一次离线跑完后，后台能查看该次的 Ragas 三项与双向 Recall@K，终端打印不算过。**在线分数不参与降级、不重路由**（对齐「demo 优先」与简述第 3 条「可观察」的字面要求）。

**KB-04 trace。** 直接沿用 needs_v9 的 `rid` + span 表方案（`llm/usage.py` 的 `span()`）：同一次知识库提问的「文档检索 → 图片召回 → LLM 生成」各落一条 span，`parent_span_id` 串成树，后台详情页可逐层展开看入参/出参/耗时。**不做第二套 trace**。注意：离线评估没有请求 `rid`，进不了 span 树，评估结果单独出报告页；`TRACE_ENABLED` 默认 `false`，演示环境要打开否则详情页看不到检索。

**KB-05 企业知识库定位。** 演示数据用「部门制度、方案设计」类文档（如一份《新员工入职指引》《某系统架构设计》），自然带章节标题、架构图、流程图，能同时喂饱 KB-01/KB-02 的演示点。**演示语料要附一份人工图文配对（问句→图片 id、图片→文本块 id）**，否则双向 Recall@K 没有 ground-truth 分母。

**KB-09 问答前台页面（第 11 条）。** 新增一个**企业知识库问答前台页面**，与现有食疗前台 `frontend/` 完全独立；前端用 **Vue**、**不用 Gradio**。**它是单独一个 Vue 应用**——食疗 `frontend/` 是静态页不是 Vue，`admin-web` 的路由都在 `/console/` 下且未登录会跳登录页，所以问答页**不落进 `admin-web` 路由、不进后台侧栏、不要求管理员或食疗手机号登录**，构建产物也不覆盖食疗首页。页面只承载**问答**：下拉框选租户、文本提问、图片提问、查看召回的块和图。录入与管理不在前台（见 KB-10/KB-11）。

### 2.4 KB-06 多租户实现（头脑风暴）

目标是「企业知识库」，多租户是绕不开的话题。方案按**成本从低到高**排列，demo 阶段优先最便宜的：

| 方案 | 做法 | 成本/隔离强度 | 适用 |
|---|---|---|---|
| A 逻辑字段隔离 | 所有文档块带 `tenant_id`，检索时加过滤 | 最低，逻辑隔离 | demo 首选 |
| B Milvus Partition | 每租户一个 `partition`，查询限定 partition | 低，物理分区 | 租户数少（< 几百） |
| C 独立集合 | 每租户一个 collection（集合名带租户后缀） | 中，隔离最干净 | 租户规模大、需独立运维 |
| D 独立实例 | 每租户一套 Milvus/PG | 最高，成本最高 | 政企强隔离，demo 不做 |

**结论（已定）**：本主题用 **A（逻辑字段 `tenant_id`）**，即所有文档块带 `tenant_id`、检索时加过滤，把「隔离怎么体现」讲清楚即可。B/C 作为演进选项写进文档，D 明确不做。与现有项目记忆里「多租户在百 DAU 是净负债」的判断一致——这里只是把「怎么实现」的答案准备好，不等于要现在上 B/C/D。

**过滤规则（写死）**：`tenant_id` 只加在知识库的文档表和新向量集合上，`kb_chunks` / `kg_entity` / 食疗业务表不加。问答请求**没带租户时不查库**；前台用下拉框选定租户再问（这个选择就是演示隔离），**本期不从登录身份推导租户，也不做租户管理页**。验收：租户 A 的已通过制度，用租户 B 提问，召回为空。

**后续演进（本期不做）**：第 10 条提到「后面可以引入角色、菜单权限做隔离」。这是**另一层维度**——多租户隔离的是「企业之间」，RBAC 隔离的是「同一企业内的角色/菜单」，两者不冲突、可叠加。本期只做租户隔离，角色/菜单权限留到有真实多用户场景时再上（对齐 brain_v2「两档角色够用时不要急着拆 RBAC」的结论）。

### 2.7 图文互搜的召回评测：沿用开源标准，不自定义

「图是否被正确召回」本质是**跨模态检索（cross-modal / image-text retrieval）**评测，这是一个独立、成熟的开源算法领域，**Ragas 不覆盖它，也不需要自定义**——标准协议就是 **Recall@K**，且天然满足「确定性」要求（不需要 LLM 打分，只做 top-K 里有没有正确项的布尔判断）。

| 指标 | 定义 | 说明 |
|---|---|---|
| **Recall@K**（核心） | 正确项出现在 top-K 结果里的查询占比 | R@1 最严（命中第 1 名才算对），R@5/R@10 更宽松 |
| **Mean Rank / Median Rank** | 正确项平均/中位排名 | 越低越好，衡量「埋得深不深」 |
| **MRR** | 正确项排名倒数的均值 | 文档图检索 benchmark（如 NL-DIR）常用 |
| **Precision@K / MAP / NDCG** | 排序感知，考虑顺序与位置权重 | 可选，若关心「最佳答案排第一」 |

**本主题落地口径**：双向 Recall@K（对齐 CLIP benchmark 的双向协议）——`文本→图` 用问句召回正确图片、`图→文本` 用图片召回正确文档块，各算 R@1/R@5/R@10。**标答只有一份人工配对**（问句→图片 id、图片→文本块 id），Recall@K 对本库的 top-K 结果与这份人工配对现算，不用关键词/正则构造正样本（避免把食疗的规则引进知识库评测）。

**可直接用的开源实现**：

- **LAION-AI/CLIP_benchmark**：`zeroshot_retrieval.py` 已实现双向 Recall@K（`image_retrieval_recall@k` / `text_retrieval_recall@k`），一行 CLI 可跑。
- **open_clip / CLIP-KD**：`get_metrics` 是标准 R@K 实现（相似度矩阵 → argsort → `mean(preds < k)`），几行可照抄。
- **Milvus / Zilliz 官方**：多模态检索评测指引即「Recall@K + NDCG + 跨模态相似度」组合。
- **NL-DIR（CVPR 2025）**：专门的**文档图片检索** benchmark，与「部门制度/方案设计里的架构图、流程图」场景高度吻合，`Recall@1 / Recall@10 / MRR@10` 是其标准口径，可直接对标。

### 2.8 待拍板问题（已定 / 结论）

1. **评估指标选型（已定）**：**分层**——有据样本跑 Ragas；图文互搜的「图是否被正确召回」沿用开源跨模态检索标准 Recall@K（详见 2.7），不自定义。
2. **嵌入模型（已定：走百炼 DashScope 在线 API）**：图文检索用 **`tongyi-embedding-vision-plus-2026-03-06`**（多模态向量，1152 维，中文原生支持），**走百炼 `MultiModalEmbedding` 接口**（复用现有百炼 key，`0.0005 元/千 token`，新开通 100 万 token 免费额度，数据不出境）。**本主题只走「独立向量」**——文本块走文本塔、图片块走图像塔，靠模型内部的图文对齐实现以文搜图/以图搜文；**不调用「融合向量」**（`text`+`image` 同 content 产出的 `fused` 向量，与纯文本/纯图向量无可比性保证，且图片提问是纯图、与「图+描述」融合向量不对等）。图片描述仍生成，但只写 `text` 字段供 BM25/回答，不进稠密向量。食疗线继续用 `text-embedding-v3`（纯文本，1024 维）。**两者维度不同（1152 vs 1024）、向量空间不同、不互通，本就不该也不需统一**——统一会动食疗线的 `kg_entity` 实体链接集合（即 `docs/brain/brain_v2.md` KGD-05 警告的坑），而让知识库迁就纯文本模型则丢掉了「图」这个核心卖点。落定：**两套模型、两套集合各自独立，集合名带模型版本后缀**（如 `kb_mm_tongyi_vision_plus_1152`，注意 Milvus 集合名只允许字母/数字/下划线，不用连字符），避免维度漂移静默混。本期**不改** `kg_entity` / `kb_chunks` 的集合名。
3. **多租户档位（已定）**：**方案 A（逻辑字段 `tenant_id`）**，见 2.4。
4. **是否动 `kb_chunks`（已定：不碰）**：企业知识库**新建独立图文集合**，不复用、不升级食疗线的 `kb_chunks`。第 10 条「补充、不推翻」已定调，两条线物理隔离。

**审核三态与向量的同步（需写死，接口返回时检索结果已符合新状态）**：

| 动作 | 文档状态 | 向量 |
|---|---|---|
| 添加 | `pending` | 不写 |
| 编辑（无论当前是通过/驳回/待审核） | `pending` | 删掉该文档已有的块 |
| 通过 | `approved` | 写入该文档的块；解析失败则保持 `pending`，不标通过 |
| 驳回 | `rejected` | 不留该文档的块 |
| 删除 | 行删除 | 删掉该文档的块和原文件 |

**审核与检索的关系**：文档主数据在 PostgreSQL，Milvus 只放「已通过」文档的块。前台检索同时带 `tenant_id` 和 `approved`，待审核 / 驳回的文档问不到。

**与食疗审核的边界**：食疗线有 `kg_candidate` / `kg_node_candidate` 候选表 + 四维打分 + `batch_id` 回滚；知识库审核**只做状态机（pending / approved / rejected）**，不引入证据分层、不引入四维打分，保持 demo 轻量。
