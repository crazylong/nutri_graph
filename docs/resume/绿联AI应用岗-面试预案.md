## 二、vLLM 部署优化参数（速查）

### 内存 / KV Cache
| 参数 | 作用 |
|---|---|
| `--max-model-len` | 最大上下文长度，直接决定 KV Cache 预留显存 |
| `--gpu-memory-utilization` | 允许占用的显存比例（默认 0.9） |
| `--max-num-seqs` | 最大并发序列数（越大并发越高、KV 块消耗越大） |
| `--max-num-batched-tokens` | 每次调度处理的 token 上限（调大吞吐、调小延迟） |
| `--enforce-eager` | 关 CUDA graph 省显存（调试用） |

### 并行 / 精度 / 量化
| 参数 | 作用 |
|---|---|
| `--tensor-parallel-size` | 张量并行，单卡放不下时切多卡 |
| `--pipeline-parallel-size` | 流水线并行 |
| `--dtype` | 推理精度（auto / bfloat16 / fp16） |
| `--quantization awq` | AWQ 4bit 量化，显存降 3-4 倍、精度损失小 |
| `--quantization gptq` / `--quantization fp8` | GPTQ / FP8 量化 |

### 调度 / 吞吐
| 参数 | 作用 |
|---|---|
| `--enable-prefix-caching` | 前缀缓存，相同 system prompt 共享 KV |
| `--enable-chunked-prefill` | 分块预填充，长 prompt 降低首 token 延迟 |
| `--num-speculative-tokens` | 投机解码，小模型草稿加速 |

## 三、KV Cache 优化措施（核心考点，按三层答）

1. **架构层**：GQA / MQA（多个 query 头共享 KV 头，KV 量按头数比例下降）——最根本，选模型时考虑。
2. **框架层**：PagedAttention（KV 按块分页，消除碎片，vLLM 招牌）；前缀缓存（复用相同 system prompt 的 KV）。
3. **数值层**：KV 量化到 int8 / fp8（显存降一半以上）；窗口注意力（只留最近 N token 的 KV）。

### 精度速记（别混）
- **fp32** 单精度浮点 32bit；**fp16** 半精度浮点 16bit；**bf16** 16bit（指数位同 fp32，训练稳）。
- **int8** = 8 位整数（量化用，不是"半精度"）；**FP8** = 8 位浮点（H100 新卡支持）。int8 ≠ FP8。

## 四、Agent 怎么做压力测试

> 一句话：普通 API 压测看 QPS/P99，Agent 压测核心是**故障注入 + 长任务状态恢复**，因为 Agent 是有状态的、会调工具的长链路。

### 三个压力维度
| 维度 | 测什么 |
|---|---|
| 并发 + 队列 | 同时 N 个任务、长任务会不会饿死短任务 |
| 工具调用 | 外部 API 延迟/失败/重试 |
| 故障注入 | 主动让工具失败、模型超时、Worker kill、DB 短暂不可用 |

### 做法
1. 合成有代表性的任务集（改代码 / 写测试 / 审查 PR / 问答），混合短任务 + 少量长任务。
2. 并发压测看队列排队、饥饿。
3. **故障注入是灵魂**：打工具失败、额度用尽、存储挂掉，看 agent 能否降级重试恢复，而不是烂尾。

## 五、Agent 中间任务失败怎么回滚

> 先分两类副作用：**可逆**（改文件、写库）能回滚；**不可逆**（下单、发消息、发邮件）不能回滚，只能补偿/告警，所以要从源头挡掉。

### 回滚策略（从轻到重）
| 策略 | 说明 |
|---|---|
| Checkpoint 快照 + 断点续跑 | LangGraph checkpointer 落库，失败从中断处继续，不重跑已完成步骤 |
| 补偿事务（Saga） | 每步配对应补偿动作（改文件→git 还原） |
| 幂等 + 批次回滚 | 写入带 batch_id，能整批删（`kg.merge --rollback bundle:3`） |
| 不可逆操作先确认 | 下单/发消息先人工确认 + 幂等 + 锁，把"需要回滚"从源头挡掉 |

## 六、我的项目案例（面试直接抛，别只讲理论）

1. **测试删了生产数据**：回滚用"包含匹配"，短批次号命中生产长批次号，删了线上 120 个节点 → 教训是"回滚边界要写死、测试生产不能共用一张图"。
2. **Neo4j 写事务没 consume 静默丢数据**：479 节点被回滚、PG 却标已合并，双写不一致无报错 → 分布式事务边界问题。
3. **下单幂等 + 锁 + confirm_id**：不可逆操作防重复，先查幂等、加锁、订单服务复价。
4. **kg.merge 的 batch_id 回滚**：每条边能追溯"谁、哪一批、凭什么写的"，精准回滚。

## 六·五、记忆分层与多轮会话恢复（多轮对话系统高频追问）

### 1. 一次会话的多轮对话存在哪？

> **短期记忆**（PostgreSQL 的 `session`/`message` 表），不是长期记忆。长期记忆只存用户画像（过敏/忌口等跨会话的稳定事实），问答链路不读不写 memory_fact 向量。

| 类型 | 存什么 | 落哪 | 用途 |
|---|---|---|---|
| 短期记忆 | 逐轮原文消息 + 滚动摘要 | PG session/message 表 | 多轮上下文，拼进 prompt |
| 长期记忆 | 用户画像（过敏/慢病/忌口） | PG user_profile 表 | 跨会话约束，进 Cypher 过滤 |

### 2. 刷新页面怎么恢复会话？

1. 会话 ID（uuid）持久化在 PG，刷新/重启都不丢。
2. 前端带着 session_id 重新请求：`GET /sessions`（列会话）+ `GET /sessions/{id}/messages`（按轮次取消息）。
3. 继续聊：`POST /chat` 带 session_id，先 `owns()` 校验"是不是本人会话"，防串号；不带则自动开新会话。
4. 恢复后上下文按「三段式」拼：**较早摘要 + 水位线未覆盖的更早原文 + 最近 3 轮原文**。

### 3. 关键细节（能讲出来很加分）

- **摘要是后台异步写的**，第 4 轮刚落库时摘要可能还没生成完。若只拼「摘要 + 最近 3 轮」，第 1 轮会两头都不在、凭空消失——所以"水位线没盖住的更早轮次"仍用原文兜底。
- **旧回答的子图卡片**（meta）可能为空，打开历史时按前面的用户问题补一次检索、只补图不重新调生成模型。

## 七、技术面反问（就这一个）

> "岗位里提到'完善应用评测、数据使用规范和质量验证机制'，我想请教下团队目前在 AI 应用的**效果评估和防幻觉**上是怎么落地的？比如用 RAGAS 这类自动化指标 + 固定评测集做回归，还是靠检索增强或知识图谱约束输出？有没有在真实业务里验证过方案差异？"

**引入语**：因为我之前在食疗项目里，就是靠"带证据等级的知识图谱 + Ragas 分层评估"管幻觉——有依据才答、没依据明确拒答，还单独评了"该拒答有没有拒答"。想了解下咱们这边是不是也有类似思路。

### 反问后可能被追问，预案：
1. "Ragas 评了什么？" → 分层：有据样本算 faithfulness/relevancy，弃答和未收录用自建确定性规则，混评会拖低分。
2. "弃答正确率怎么保证？" → 确定性规则（关键词+正则）不花 LLM、可复现，交模型反而不稳定。
3. "知识图谱比纯 RAG 好在哪？" → 结构上区分民间说法 vs 医学禁忌，按证据等级过滤，纯向量分不清。
4. "评测集怎么维护？" → 75 条固定集，三类（有据/应弃答/未收录），分层算指标。
